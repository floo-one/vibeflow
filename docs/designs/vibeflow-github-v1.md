## Problem Statement

VibeFlow works and is used every day (reading and dictation milestone 1 done 2026-10-06, 211 core tests), but it lives only on one Mac with no remote. The goal is to store a solid, finished-looking v1 on GitHub. Launching and distribution are explicitly out of scope for now: "i just wanna store a solid v1 on github and store it there. all the launching and distribution doesnt matter for now."

The first people who will open the link are "prolly some friends. not very tech afine". They set up their own keys: "they gotta set it up themself."

## What Makes This Cool

Each half already exists on its own. Research notes from one web search on 2026-10-06, unverified beyond those results: dictation has FreeFlow (search result said about 2,600 stars), VoiceInk and WhisperDictation; read-aloud has Hibiki (ElevenLabs), aloud-tts and Sotto (both Kokoro). In that search no app combined speech in, speech out and "explain this like I'm 10" in one small native app. Treat that as a hunch, not a fact: the README describes what VibeFlow does and makes no "only app that" claims. "Hear anything. Say anything." is the working tagline.

Two details make it feel finished rather than a weekend clone. Tables, links and Markdown are rewritten for listening. Dictation pastes into the exact field you were typing in and puts your clipboard back.

## Constraints

- Free Apple personal team only: no Developer ID, so no notarization. Homebrew casks now require signed and notarized apps (Homebrew discussion #3088). That is why v1 ships no binary at all (see Distribution Plan).
- Settings must stay minimal: four tabs, a dropdown per voice, model and device (user feedback 2026-10-05 and 2026-10-06).
- Bring your own keys (ElevenLabs, Anthropic, Groq). No server, no accounts, no telemetry.
- Builds need Xcode 26 and XcodeGen; the deployment target is macOS 15. On-device dictation needs macOS 26.

## Premises

1. The goal is a solid v1 stored publicly on GitHub. Launch, stars and distribution come later, if at all. v1 is a source and showcase repo: friends see what it does from the README, and actually running it waits for a downloadable build (TODO P3) or the author's help building it on their Mac.
2. The pitch is both directions in one app, not "another Whisper dictation app".
3. People set up their own keys in Settings > Keys. A guided onboarding flow is a later TODO.
4. No notarized build or Homebrew cask for now.

## Approaches Considered

### Approach A: Just push it
Clean up secrets, refresh the README, tag v1.0.0, push. Ruled out: nothing would catch a future change that breaks the build, and the repo would look unfinished when shown.

### Approach B: Solid v1 (chosen)
README with a hero line, screenshots and a keys table. GitHub Actions running the tests and an app build on every push. A v1.0.0 tag with a CHANGELOG and release notes. A privacy and secrets sweep, and notes on signing for anyone who forks it.

### Approach C: Solid v1 plus a talking README
B plus an audio clip of VibeFlow reading its own README. Deferred: fun and on-brand, but not needed to store v1.

## Recommended Approach

Approach B. The pieces, in order:

1. **Privacy and secrets sweep (done in this session, results below).**
   - API keys: none in any of the 29 commits (pattern scan for ElevenLabs, Groq and Anthropic key shapes returned 0). `.env` is gitignored and was never committed.
   - Commit identity: all 29 commits are authored and committed as `the current author identity (personal domain email)`. Pushing publishes that address permanently. Decision for the user before the first push: keep it (own domain), or rewrite history to a GitHub noreply address with a mailmap filter, which is only possible before the first public push.
   - Personal details in tracked files: "Florian" in TODOS.md, the v2 design doc and one LiveEvalTests fixture email; the full name in LICENSE (intended). The Apple team ID `Y798SH49X3` is in project.yml and CLAUDE.md.
   - Tracked `.claude/` and CLAUDE.md: see Open Questions. They block other Claude Code users today.
   - Ongoing protection: enable GitHub secret scanning and push protection on the repo in step 5 (free for public repos), so a later commit cannot publish a key.
2. **README.**
   - A hero line plus a one-sentence description, then two screenshots in `docs/images/`: the menu bar menu and Settings > Reading. Capture rule: neutral sample text, no pending or failed dictation in the menu, a premade ElevenLabs voice selected, never the Keys tab. Review both images before committing them.
   - The three features (read, smart read, dictate) with their default shortcuts.
   - Bring every Settings path and feature claim in line with the four-tab UI. "What leaves your Mac" and the feature list still mention Settings > Apps, the per-app "Keep this app on this Mac" switch, per-app instructions and the vocabulary list. Remove those mentions, or say plainly "not in Settings yet". Settings > Dictation > Microphone and Reading > Speaker stay.
   - A keys table with columns for what each key enables, where to get it, its free tier, and what happens without it:
     - ElevenLabs: without it, reads use the best installed Apple voice.
     - Anthropic: without it, smart read is unavailable.
     - Groq: without it, dictation uses Apple's on-device recognizer on macOS 26 and does not work on macOS 15.
     - The smallest useful setup is a Groq key alone (free tier).
   - "Build it yourself":
     - Xcode 26, `brew install xcodegen`, `xcodegen generate`.
     - Running the app needs a free personal team in Xcode, so the Accessibility and Microphone permissions survive rebuilds. Ad-hoc signing (CI only) loses the Accessibility grant on every build.
     - A forker changes `DEVELOPMENT_TEAM` and `bundleIdPrefix` in project.yml. The bundle ID `one.floo.vibeflow` belongs to the author's team, so automatic signing with another team needs its own bundle ID. This was not verified with a second team; the README states the steps that avoid the conflict.
3. **CI.** Add `.github/workflows/ci.yml`. It assumes a public repo, where macOS minutes are free.
   - Triggers: push to main and pull requests.
   - Steps: select Xcode 26 explicitly; fail early with a clear message if `xcodebuild -version` reports a major version below 26. Then `cd VibeFlowCore && swift test`, `brew install xcodegen && xcodegen generate`, and an ad-hoc app build (`CODE_SIGN_STYLE=Manual CODE_SIGN_IDENTITY=- DEVELOPMENT_TEAM=`).
   - LiveEvalTests run only with `VIBEFLOW_RUN_EVALS=1` plus an API key. The workflow sets neither the flag nor any secrets.
   - If the repo turns out private: restrict triggers to main with path filters, and cache SwiftPM, before enabling CI.
4. **Version 1.0.0.** Set `CFBundleShortVersionString` to 1.0.0 in project.yml. Write a `CHANGELOG.md` with the v1.0.0 notes: reading, smart read, dictation, minimal Settings, speakable text, the silent-recording fix. Commit; no tag yet.
5. **Create the repo and release, in this order.**
   - Confirm visibility with the user, then `gh repo create floo-one/vibeflow` with a description and topics (macos, swiftui, text-to-speech, dictation, elevenlabs, whisper, menu-bar).
   - Enable secret scanning and push protection.
   - Push main only. Wait for the first CI run to go green.
   - Then tag `v1.0.0` on that exact commit, push the tag, and create the GitHub Release with the CHANGELOG notes and no binary.
6. **TODOS.md.** Add:
   - A guided onboarding flow for keys (P2).
   - A downloadable build: a notarized DMG plus a Homebrew cask, needing the $99 Developer ID, once people beyond friends want to run it (P3).
   - Bringing vocabulary and per-app settings back to the UI (P3).

## Open Questions

- Public or private repo? Assumed public (MIT, open source). Confirm before `gh repo create`.
- Keep the `Florian` mentions in TODOS.md, the v2 design doc and the eval fixture, or neutralize them to "the user"? Recommendation: keep; it's the author's own project.
- Keep `.claude/` and CLAUDE.md public? Effect on others today: `.claude/hooks/check-gstack.sh` is a PreToolUse hook that denies every Skill call for a Claude Code user without gstack, and CLAUDE.md tells agents to stop when gstack is missing. A forker opening the repo in Claude Code is blocked. Recommendation: keep CLAUDE.md's build and debugging notes, drop the hook from the repo, and turn the gstack section into "the author uses gstack" guidance instead of a hard stop.
- Should the team ID and bundle ID move out of project.yml (for example to a gitignored local xcconfig) so forks build without editing tracked files? Recommendation: keep both in project.yml with a comment. The README tells forkers which two values to change; CI uses the ad-hoc override.
- Which macOS runner image ships Xcode 26 on GitHub Actions today? Verify when writing the workflow. The version guard in step 3 fails loudly if the chosen image has no Xcode 26.
- Keep the commit email `the personal domain email` public, or rewrite to a noreply address before the first push? See step 1.

## Success Criteria

- The repo exists on GitHub with main pushed, and `v1.0.0` tagged on a commit whose CI run is green.
- CI is green on main: core tests and the ad-hoc app build, with the Xcode 26 guard.
- The README renders with both screenshots, the keys table and build steps. A non-technical friend can tell what the app does from the first screen. Running it is not a v1 criterion (Premise 1).
- Every Settings path the README mentions exists in the four-tab UI.
- No API keys or other secrets in the repo or its history, and secret scanning plus push protection are on.

## Distribution Plan

No binary distribution for v1: the GitHub Release carries notes only, and people build from source with a free personal team (see README step). Friends who are not technical cannot run it yet; that is accepted for v1 (Premise 1). The future path (TODO, P3) is a $99 Developer ID, then a notarized DMG on GitHub Releases, then a Homebrew cask.

### R2-1 — feasibility

**Problem**

> Step 2 ('A forker changes DEVELOPMENT_TEAM and bundleIdPrefix in project.yml') and the team/bundle ID Open Question ('The README tells forkers which two values to change') name a setting that does nothing here. project.yml hard-codes `PRODUCT_BUNDLE_IDENTIFIER: one.floo.vibeflow` in the VibeFlow target settings (line 65). That explicit value overrides `options.bundleIdPrefix: one.floo`. A forker who follows the README still builds with one.floo.vibeflow, so the App ID conflict with team Y798SH49X3 that the step is meant to avoid is still there.

**Remedy**

> Have the README and the project.yml comment tell forkers to change `PRODUCT_BUNDLE_IDENTIFIER` (and `DEVELOPMENT_TEAM`). Or derive the bundle ID from the prefix, for example remove the explicit PRODUCT_BUNDLE_IDENTIFIER so XcodeGen's `bundleIdPrefix` + target name applies, and confirm the generated value is still one.floo.vibeflow. Then update 'which two values to change' to match.

### R2-2 — completeness

**Problem**

> The commit-email decision (step 1, Open Questions, Next Steps 1) offers 'rewrite history to a GitHub noreply address with a mailmap filter', but no ordered step carries it out. Next Steps goes straight from resolving the question (1) to creating the repo and pushing (6), with no rewrite step before the push. Nothing sets the noreply address for future commits either: the local identity stays `the current author identity (personal domain email)`, so the first commit after the rewrite would publish the address again.

**Remedy**

> Add a conditional step between step 5 (version commit) and the first push: if the noreply option is chosen, rewrite author and committer emails across all commits, check with `git log --format='%ae %ce' | sort -u`, and set `user.email` to the noreply address in this repo's git config. Optionally enable GitHub's 'Block command line pushes that expose my email'. Note that the rewrite changes every commit hash, so any docs that cite hashes go stale.

### R2-3 — completeness

**Problem**

> The `.claude/` Open Question recommends dropping `.claude/hooks/check-gstack.sh` (and its PreToolUse entry in `.claude/settings.json`) and turning CLAUDE.md's 'If GSTACK_MISSING: STOP' section into guidance. ### R2-4 — consistency

**Problem**

> The keys table says 'The smallest useful setup is a Groq key alone (free tier)'. That contradicts the table's own fallbacks. With no keys at all, reading works with the best installed Apple voice. On macOS 26, dictation also works with no keys through the on-device recognizer. A Groq key is only the smallest setup for dictation on macOS 15. A non-technical friend reading the README may think a key is required before anything works.

**Remedy**

> Replace the line with the real minimum per goal. For example: no keys, read aloud with an Apple voice, plus dictation on macOS 26. Groq key (free tier), dictation on macOS 15 and better transcription. ElevenLabs, premium voice. Anthropic, smart read.

### R2-5 — consistency

**Problem**

> Step 1 relies on secret scanning and push protection that are 'free for public repos', and the Success Criteria require 'secret scanning plus push protection are on' with no condition. Visibility is still an open question, and step 3 gives a private-repo fallback only for CI. On a private personal repo these features need paid GitHub Secret Protection, so if the user picks private, the success criterion cannot be met for free and the ongoing-protection guarantee has no fallback.

**Remedy**

> Add a private-repo branch next to the CI one. Either accept the paid feature, or use a free local guard (for example a gitleaks pre-commit hook or a gitleaks CI step) and make the success criterion conditional on visibility.
