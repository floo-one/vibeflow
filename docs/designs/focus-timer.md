# Design: Focus timer (Flow-style Pomodoro in the menu bar)

Generated by /office-hours on 2026-11-02

Status: APPROVED

## Problem Statement

Florian runs the Flow app (macOS Pomodoro timer) next to VibeFlow. VibeFlow is their own opinionated Mac utility that absorbs small third-party apps (the German clock replaced Second Clock). They want a focus timer inside VibeFlow that is "customizable, but still easy to set up" and mirrors the Flow features they actually use: a menu bar countdown, the focus / short break / long break cycle, and stats. Done means they can quit Flow.

## What Makes This Cool

Not novelty: the user said "doesnt have to be super special for the start." The payoff is one fewer app, a countdown you read at a glance, and a menu that shows today's blocks and a 7-day strip, so finishing a block feels like progress. VibeFlow-only twists (meeting-aware sessions, spoken transitions, notch progress, dictated titles) are parked for later. They are cheap to add once the engine exists.

## Constraints

- Settings stay minimal (user rule): plain dropdowns, strong defaults, at most a toggle. Settings gets one row for this feature.
- No database, no server. Stats are a JSON file in Application Support.
- Swift 6 / SwiftUI `MenuBarExtra`; core logic in VibeFlowCore with Swift Testing, as for Clock and Meetings.
- Public repo: nothing personal in code or fixtures.
- Release and Debug run side by side ("VibeFlow" and "VibeFlow Dev"). Each needs its own log file, or Debug runs pollute the real stats. Debug writes `focus-dev.json` (see FocusLog).

## Premises (agreed)

1. Plain Flow clone: menu bar countdown, focus / short break / long break cycle, stats. No app/website blocking, no calendar or voice tricks in v1.
2. Customizing means picking a preset. **Each preset carries its own cadence** (revised after the second opinion):
   - Classic: 25 focus / 5 break / 15 long break after 4 blocks
   - Long: 50 / 10 / 20 after 3
   - Deep: 90 / 20 / 30 after 2

   No Custom preset in v1.
3. When a phase ends, VibeFlow plays a chime and posts a notification, then waits for a click. No auto-continue and no toggles for it.
4. The running session and the stats go in **one JSON file**, `focus.json`, with **no pruning**, using HistoryStore's atomic-write pattern but not its retention (eng review D2). Only completed focus blocks are recorded, each exactly once.
5. The timer is its own `MenuBarExtra(isInserted:)`, like Clocks and Meetings, shown while Focus is switched on.
6. The timer survives sleep and relaunch. The persisted state in `focus.json` is session ID, phase, selected preset, deadline, paused-remaining, cycle position, block index, block start, block preset snapshot, and a logged flag for the current block. On wake or relaunch the engine finishes at most the current phase and waits for a click. It never invents missed cycles. Sleep counts toward the scheduled interval, and stats mean "completed timer minutes", not measured attention.

## Approaches Considered

- **A: Timer inside the main VibeFlow menu.** Smallest diff, but there's no countdown to glance at, so it doesn't replace Flow. Rejected.
- **B: Its own Focus menu bar item.** Chosen.
- **C: Countdown attached to the Clocks item.** Saves menu bar space, but it only works with Clocks on and couples two unrelated features. Rejected.

## Recommended Approach (B)

Wireframe (approved): [focus-timer-wireframe.png](focus-timer-wireframe.png).

**Menu bar label**
- Running: `18:22`, monospaced digits.
- Paused: the remaining time, dimmed or with a pause glyph.
- Phase ended: `Break?` or `Focus?`.
- Idle: a timer SF Symbol only.

**Menu**
- Running: phase and preset name, a large countdown, cycle dots (filled = done, ring = current), Pause / Skip / Stop.
- Paused: the remaining time, Resume / Stop.
- Awaiting break: primary "Start break (5 min)" (or the long break), Skip break, Stop.
- Awaiting focus: primary "Start focus (25 min)", Stop.
- Idle: "Start focus (25 min)".
- The popup stays open after a button click and closes when you click elsewhere (eng review D3).
- Always: "Today · N blocks · M min", a 7-day bar strip (focus minutes per day, today on the right), and the preset dropdown at the bottom.

**Menu style:** the Focus item uses `.menuBarExtraStyle(.window)`. The custom countdown, cycle dots and bar strip need a SwiftUI window, and the countdown must keep ticking while the menu is open. This is the first `.window` item in the app, because Clocks and Meetings use the default `.menu` style.

**Settings:** one toggle, "Focus timer in menu bar", in General. It **defaults to off**: the Sparkle update must not add a menu bar item for anyone who didn't ask for it. Switching it off while a session is running, paused or waiting stops the session: the partial block is not logged, the delivered notification is removed, and the cycle resets. Switching it back on starts at idle. The preset lives in the menu, where you use it, and is stored in Preferences under `focus.preset`.

**Preset changes:** the dropdown stays enabled. A change applies from the next phase: a running or paused phase keeps its deadline or remaining time. While awaiting, a change recomputes the awaiting phase and its duration and replaces the delivered notification with one for the new phase. Engine test included. The cycle keeps the real count of completed blocks, which is never clamped (eng review D7). The long break is due when that count reaches the selected preset's `blocksBeforeLong`, and the dots show the count up to that number. Switching from Classic with 3 done to Deep and back to Classic still has 3 done. Tested.

**Cycle rules**
- A completed focus block advances the cycle position and is logged.
- A skipped focus block is neither logged nor counted toward the long break, and goes to the awaiting-break state.
- Skipping a short break, whether it is running or awaiting, goes to awaiting focus with the count unchanged.
- Skipping the long break, whether it is running or awaiting, resets the cycle, the same as finishing it (eng review D7).
- The cycle count resets after the long break ends (completed or skipped), on Stop, and when Focus is switched off. It never resets just because a new day starts.

**Core (VibeFlowCore/Focus/)**
- `FocusPreset`: enum with focus, short, long and `blocksBeforeLong`.
- `FocusEngine`: a pure state machine `idle → running(phase, deadline) ⇄ paused(phase, remaining) → awaiting(nextPhase) → running …`. It takes `now` as input and never reads the clock itself. Every command first expires a phase whose deadline has passed, using the same `now`, then applies to the resulting state (eng review D7). A Pause clicked just after zero acts on awaiting break, and the block is still logged. Tested. Skip ends a phase without logging. Stop resets the cycle.
- `FocusLog`: owns one file, `focus.json` shaped `{active: Session?, blocks: [Block]}` (eng review D2). Release writes `~/Library/Application Support/VibeFlow/focus.json`. Debug (`#if DEBUG`) writes `focus-dev.json` in the same folder, because both builds share Application Support and dev runs must not touch the real stats. Every change (start, pause, expire, skip, stop) is one atomic write with 0600 permissions, like HistoryStore, so the session and the blocks can never disagree. A block's `{id, start, end, preset, minutes}` is added in the same write that moves the session to awaiting.
  - Loading drops duplicate block ids (eng review D6). An update or scripts/dev.sh can leave the old copy running for a few milliseconds next to the new one, and this closes the only real damage, a doubled block. Tested.
  - A new session ID is created on every Start from idle. `blockIndex` counts the focus blocks started in that session (skipped ones included), only ever goes up, and is never reset by the cycle reset. `id` is `<sessionID>-<blockIndex>`. A test runs two full cycles in one session and checks that every block is logged once.
  - Each focus block takes a snapshot of its preset when it starts, and the block uses that snapshot's `preset` and `minutes`. A Classic block finished after switching to Deep logs as Classic, 25 minutes. Tested.
  - Save first, then commit (eng review D5): the next state is written to focus.json first and applied in memory only if the write succeeded. On failure the timer keeps its previous state, logs .notice and shows "Couldn't save focus data" in the popup, and the previous file stays intact. Tested with a failing write.
  - `start` is when the block first started, not the last resume. `end` is the deadline the timer reached zero at, not the time the expiry was processed after wake. `minutes` is the preset's focus length, with pauses not counted. If decoding fails, move the bad file aside under a name derived from the active file (`focus.broken-<date>.json`, or `focus-dev.broken-<date>.json` in Debug) instead of starting empty silently, because a lost file is lost history.
- `FocusStats`: pure functions for today's count and minutes and the per-day minutes for the last 7 days. A whole block counts on the local calendar day of its `end`. That covers a block that crosses midnight and one that expired during sleep and was processed the next morning. Tests cover both cases.
- The active session lives in `focus.json` next to the blocks (premise 6 lists its fields). Relaunch tests rebuild the state from that file alone.

**App (VibeFlow/)**
- `FocusTimer`: @MainActor @Observable. Owns the engine and the log, and runs a 1-second ticker only while a phase is running (MenuBarClock ticks per minute, so it can't drive this). At the deadline it calls the engine's expire, plays a chime with NSSound like LiveServices, and posts a notification.
- Re-evaluates on `NSWorkspace.didWakeNotification` and at launch.
- The popup's "Today" and 7-day strip are computed from the existing per-minute `MenuBarClock.now`, so they roll over at midnight even while the timer is idle and its ticker is stopped (eng review D7).
- Notification: `UNUserNotificationCenter` with a category action "Start break" / "Start focus" that calls the same engine method as the menu. This is VibeFlow's first use of UserNotifications: the permission is requested on the first Start, and if it's denied the chime and the `Break?` label still work.
  - The delegate is set in `AppDelegate.applicationDidFinishLaunching`, so actions work even if the menu was never opened.
  - The notification is silent (`content.sound = nil`), so the NSSound chime is the only sound.
  - `userInfo` carries the session ID, the block index and the expected next phase. The action runs only if the engine is still awaiting exactly that phase for that block in that session. Anything else is a stale action and is ignored. The guard is a pure FocusEngine method, so FocusTests covers it.
  - Every exit from awaiting (Start from the menu, Skip, Stop, a preset change, switching Focus off) removes the delivered notification.
- `FocusMenuView` holds the three states from the wireframe. The fourth `MenuBarExtra(isInserted:)` sits in VibeFlowApp, bound to `preferences.focusEnabled` with a no-op setter like Clocks and Meetings, so only the Settings toggle turns Focus off.
