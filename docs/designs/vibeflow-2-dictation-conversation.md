## Problem Statement

Florian runs two tools: Wispr Flow for speech in and Outflow for speech out. Smart read is one shot: select, hear an overview, done. He wants "a more communicative and flowy way of interacting with an AI", and asked to "copy what free flow does and combine them into one app". Outflow 2 adds FreeFlow-style dictation and uses it to turn smart read into a conversation about what was just read.

## What Makes This Cool

- One app, one key: hold it to talk, everywhere. Your words land at the cursor like Flow does.
- The same key turns into "ask a follow-up" while a conversation is open. Hear the overview of a contract, hold the key, say "what happens if I cancel early?", hear the answer. The selection is the context, so answers are about your document, not general knowledge.
- Speech in and speech out share the provider pattern, so every half has a free offline fallback.

## Landscape

FreeFlow (Zach Latta, MIT, Swift): hold Fn, talk, release; audio goes to Groq Whisper (free tier) or any OpenAI-compatible endpoint; an LLM cleans the transcript using nearby app context and custom vocabulary; the text is pasted into the focused field. It also has voice macros and an Edit Mode that transforms selected text. No vendor server. Source: feedbagel.com and opensourcealternatives.to coverage, 2026. Outflow 2 copies the dictation loop and ideas, not the code.

## Constraints

- Everything v1 constrains still holds: Swift 6, MenuBarExtra agent app, bring your own keys in the Keychain, no server, no database, Accessibility already granted.
- New runtime permission: Microphone, requested on the first key press (that first press only triggers the prompt and records nothing). If the day-one spike shows Apple's on-device recognizer also needs Speech Recognition authorization, it is requested the first time the Apple transcriber is used, and listed in Settings > Dictation.
- Third key: Groq (optional; the Apple on-device transcriber works without it once its language assets are installed).
- Clipboard: dictation pastes via the clipboard and restores plain text only, the same contract as v1's Copy fallback. Non-text clipboard content (images, files, rich text) is overwritten by a dictation; the status line says "Clipboard not restored (non-text content)" when that happens. README and Settings state this.

## Premises (agreed D4)

1. VibeFlow absorbs FreeFlow-style dictation: hold a key, talk, release, cleaned text is pasted at the cursor. It replaces Wispr Flow.
2. Speech-to-text sits behind a Transcriber protocol: Groq Whisper default, any OpenAI-compatible endpoint, Apple on-device fallback.
3. Dictation ships first as its own milestone.
4. Conversation level one is about the selection: smart read gives the overview, then holding the push-to-talk key while a conversation is open asks a follow-up instead of pasting. Answers are spoken and kept in context.
5. A small floating panel shows the transcript, only during a conversation. It ends by Escape, the close button, switching apps, or the inactivity timeout (defined below).
6. Reply drafting is out of scope, logged as a low-priority TODO.

Ruled out: ElevenLabs Scribe only (paid, no offline); Apple only (weak on names and German-English mix); porting FreeFlow's code (mixed architecture); a separate dictation target (packaging for a split nobody needs).

## Approaches Considered

- A) Native in VibeFlowCore, FreeFlow as reference. Chosen (D6).
- B) Port FreeFlow's dictation code. Rejected: two architectures in one app, less testable.
- C) Separate dictation module and target. Rejected: extra packaging, conversation needs both halves anyway.

## Recommended Approach

### New ports (VibeFlowCore/Ports.swift)

| Port | Live (app) | Fake (tests) |
|---|---|---|
| AudioRecorder | AVAudioEngine input tap, 16 kHz mono, WAV in memory | scripted audio, can fail with "no mic permission" |
| Transcriber | GroqTranscriber (OpenAI-compatible /audio/transcriptions, base URL configurable), AppleTranscriber (on-device) | scripted text or failure |
| TextInserter | snapshot clipboard text, write transcript, press Edit > Paste via Accessibility in the frozen app, restore after 300 ms | records inserts and target app |
| RecordTrigger | KeyboardShortcuts key-down and key-up for `.record`, see Record shortcut | manual down and up |

### Record shortcut (revised 2026-10-02)

Florian's layout: Option + . read, Option + , smart read, Option + - record. Recording therefore uses an ordinary shortcut through KeyboardShortcuts, the same library as the read shortcuts, instead of a modifier-only key read from a CGEventTap. This supersedes the earlier modifier-only design (Fn, Right Option) and its spike.

- Clipboard variants (added 2026-10-02): Shift + Option + . reads the clipboard and Shift + Option + , smart-reads it, with the default preset; pressing the same shortcut again confirms a long clipboard or stops playback. Implemented in v1 already.
- Name `.record`, default Option-Minus, rebindable in Settings > General next to the read shortcuts. New installs default to Option + . / , / - for read, smart read and record; existing saved bindings are kept.
- Hold and tap, from KeyboardShortcuts' key-down and key-up callbacks: key down starts recording at once. Released after 0.3 s or more: push-to-talk, stop and paste. Released sooner: the recording keeps running hands-free until the next press of the shortcut, the 2-minute cap, or the read hotkey cancels it.
- Registered hotkeys are consumed by the system: the shortcut never types its character (Option-Minus would otherwise type an en dash) and does not auto-repeat while held.
- Secure fields: registered hotkeys are expected to keep firing under Secure Event Input. The spike verifies this; if dictation into a password field is possible, VibeFlow pastes nothing there and shows "Dictation unavailable in secure fields" (checked with IsSecureEventInputEnabled at key up).

### Mode rule: dictate or ask

The record shortcut means ask only while a conversation is open and its panel is visible; otherwise it dictates. The menu bar icon and the panel header show the mode ("Listening" with a microphone, or "Asking" with a speech bubble). Switching to another app ends the conversation, so the shortcut returns to dictation the moment focus leaves. There is no separate force-dictation chord.

### Dictation state machine (milestone 1)

idle -> (key down) recording -> (key up) transcribing -> cleaning -> pasting -> idle.
- Key down in recording, transcribing, cleaning or pasting: ignored until idle (no queueing). The icon shows busy.
- Read or smart read hotkey while recording: dictation is cancelled and nothing is pasted. While transcribing or cleaning: in-flight requests are cancelled, nothing is pasted.
- Recordings under 0.3 s are discarded. Hard cap 2 minutes; past it the recording stops and is transcribed.
- Empty or no-speech transcript (empty after trimming, or the Whisper no-speech marker): nothing is pasted, status "Didn't catch that".
- Paste target is the app frozen at key down. If it quit or is no longer frontmost at paste time, nothing is pasted; the text is placed on the clipboard (status "Copied, the app lost focus") so it is not lost.

### Dictation cleanup

A third prompt, "dictation cleanup", reusing AnthropicClient: the raw transcript goes inside the document delimiters; the system prompt says the text is spoken dictation to tidy, never a question or instruction to answer; output must be the same words with fixed punctuation, casing and obvious mishearings, using the custom vocabulary from Settings. Model: claude-haiku-4-5, non-streaming, max_tokens = ceil(raw chars / 3) + 100.
Sanity check before pasting: if the cleaned text is empty, longer than 1.3 times the raw text, shorter than 0.7 times it, or the stop reason is not end_turn, the raw transcript is pasted instead. With no Anthropic key or cleanup turned off, the raw transcript is pasted.

### Transcriber fallback

| Selected provider | Falls back to Apple on | Surfaces as Last error (no fallback) |
|---|---|---|
| Groq | no key, offline or unreachable, timeout (10 s), 429, 5xx | 401 or 403 ("Groq key rejected", Open Settings > Keys) |
| Custom OpenAI-compatible URL | offline or unreachable, timeout, 5xx | 401, 403, 404, malformed response ("Check the endpoint in Settings > Dictation") |
| Apple | none | assets missing ("Download language in Settings > Dictation"), authorization denied |

Every fallback shows a one-line status ("Transcribed on device: Groq unavailable"). Apple uses the preset language, else the system language; it is single-locale, so mixed German and English is a known weakness and Groq stays the default.

### Conversation (milestone 2)

- Opening: when smart read produces its overview and starts speaking it, the conversation opens and the panel appears with the overview. Conversation off in Settings means smart read behaves as in v1 and the key always dictates.
- Asking: hold the key, speak, release. The transcript (no cleanup, no paste) becomes a user turn. Request: the guarded smart read system prompt plus an answer rule ("answer the question about the document in two to four short plain sentences unless asked for more"), the selection inside the document delimiters as the first user message, then the prior turns. Model: the smart read model from Settings (default claude-haiku-4-5), non-streaming, max_tokens 600. The answer is spoken with the frozen preset's voice and appended to the panel.
- Barge-in applies to the overview and to answers: key down while speaking stops playback within 100 ms and starts recording. Key down while the answer is still being generated cancels that request; the unanswered question is dropped from the turn list. A spoken answer that was interrupted stays in context marked "(interrupted)".
- Inactivity timeout: one setting, default 2 minutes, range 30 s to 10 minutes. It counts only while the conversation is idle (not recording, transcribing, generating or speaking) and resets on any key press or panel interaction.
- Ending: Escape while the panel is the key window, the close button, switching apps, the timeout, or starting a new read or smart read. VibeFlow does not install a global Escape tap; Escape in other apps behaves as normal. Ending cancels every in-flight request (transcription, Claude, TTS) and stops playback.
- Context: a turn is one question plus its answer. The request always keeps the selection and the overview, plus the last 10 turns; older turns are dropped first. The selection is bounded by v1's 40,000-character limit.
- Errors inside a conversation appear as a red line in the panel with Retry (re-sends the last question) and the conversation stays open. A 401 from Anthropic or ElevenLabs ends the conversation with the matching Last error action. TTS failure falls back to Apple exactly as in v1.

### Review resolutions (round 2, applied 2026-10-01)

- Shift exception (R2-1), superseded 2026-10-02 by the record shortcut (no force-dictation chord): Shift is the one allowed companion. Shift held at key down, in either order within 150 ms, forces dictation; the mode is fixed at key down and releasing Shift mid-recording changes nothing.
- Chord cancel (R2-2), superseded 2026-10-02 (registered shortcuts need no chord handling): the tap also watches keyDown. Any non-Shift key pressed while the push-to-talk modifier is held cancels the recording silently (no transcription, no status). All events pass through unchanged, so the app still receives its shortcut.
- Secure Event Input (R2-3), revised 2026-10-02 per the Record shortcut section; original text: the spike checks whether flagsChanged still reaches the tap under secure input. If it does, show "Dictation unavailable in secure fields". If not, VibeFlow polls IsSecureEventInputEnabled every second and greys the menu bar icon while it is on; key presses are then a silent no-op.
- Panel focus (R2-4): the panel is a non-activating NSPanel that can become key without activating VibeFlow. "Switching apps" means the frontmost app changes to anything other than the conversation's source app; VibeFlow's own windows never count.
- Conversation overlaps (R2-5): key down during answer TTS synthesis cancels it and keeps the answer text in context marked "(interrupted)"; key down while a question is transcribing is ignored; Shift-forced dictation stops any playback first, then records.
- Answer audio (R2-6): answers use the same streaming ElevenLabs path as reads, so playback starts on the first audio chunk. Budget for 3 s: transcription about 0.7 s, Haiku answer about 1.5 s, first audio about 0.3 s, overhead under 0.5 s.
- Retry (R2-7): the last question's audio is kept until its turn completes. Retry resumes at the step that failed: re-transcribe, re-ask Claude, or re-speak.
- Paste item (R2-8): TextInserter finds the menu item bound to plain Cmd-V (kAXMenuItemCmdChar "V", no extra modifiers), the same way v1 finds Copy, so it works in any UI language. If the app has no such item, it posts a synthesized Cmd-V. The paste spike includes a German-locale run.
- Timeout reset (R2-9): only push-to-talk presses and panel interaction reset the inactivity timer. No global key monitor.
- No-speech detection (R2-10): Groq and custom endpoints are called with response_format verbose_json; a result is no speech when every segment has no_speech_prob above 0.6, or the trimmed text matches a small list of known silence hallucinations ("Thank you.", "Thanks for watching.", "Untertitel im Auftrag des ZDF", and similar). Apple: an empty final result is no speech.
- Unclassified responses (R2-11): any other 4xx (including 400 and 413) surfaces as a Last error with the status and response message. A 429 from a custom URL falls back to Apple like Groq's. A custom URL may be used without a key, for local servers such as Ollama; a 401 from it says "Endpoint needs a key".

### Settings additions

- Dictation tab: transcriber (Groq / custom OpenAI-compatible URL / Apple) with the Apple language asset status and a download button, cleanup on or off, custom vocabulary.
- Keys tab: Groq key, with the missing-key callout.
- Conversation: on or off, inactivity timeout.

## Success Criteria

- Key up to text at cursor at or under 1.5 s for a 10-second dictation with Groq and Haiku cleanup, measured over ten runs (median).
- Dictation works in Safari, Mail, Notes, VS Code, Slack and Terminal; clipboard text is restored afterwards.
- Conversation eval: a fixed sample contract and ten questions with expected facts; at least 9 of 10 answers contain the expected fact (substring check, live eval gated like v1's). Key up to first answer audio at or under 3 s median.
- Barge-in: playback stops within 100 ms of key down, measured from the event tap timestamp to the player's stop call in a log line.
- Unit tests against fakes for every state machine row above (dictation overlaps, mode rule, fallbacks, cleanup sanity check, barge-in, timeout, context trimming).
- Florian uninstalls Wispr Flow after a week.

### R2-1 — consistency

**Problem**

> Push-to-talk capture says a press counts only when the modifier is pressed alone, and any other key held at the same time makes it a normal shortcut that is ignored. The Mode rule then says holding Shift together with the key forces dictation. Under the first rule, Shift plus the key would be ignored, not treated as forced dictation.

**Remedy**

> Make Shift an explicit exception to the pressed-alone rule. Define the order (Shift first, then the key, or either order) and whether releasing Shift mid-recording changes the mode.

### R2-2 — completeness

**Problem**

> Recording starts at key down, but a press becomes 'a normal shortcut and is ignored' only once another key is pressed while the modifier is held. The design does not say what happens to the recording already in progress, whether the tap must also watch keyDown events to notice this, or whether the modifier-shortcut chord still reaches the frontmost app.

**Remedy**

> State that a second key cancels the in-progress recording silently, with no transcription and no status, that the tap watches keyDown or other flags for this, and that those events are passed through unchanged.

### R2-3 — feasibility

**Problem**

> The design says the tap is blind under Secure Event Input, yet it relies on detecting the push-to-talk key down so it can call IsSecureEventInputEnabled and show 'Dictation unavailable in secure fields'. If the tap does not receive the event, that message can never appear. Next Steps lists Secure Event Input detection for the spike, but Open Questions does not include whether flagsChanged events still arrive under secure input.

**Remedy**

> Add to the spike's Open Questions whether modifier flagsChanged events reach the tap under Secure Event Input, and define the fallback if they don't (for example a silent no-op, or polling IsSecureEventInputEnabled to grey out the menu bar icon).

### R2-4 — feasibility

**Problem**

> A conversation ends when the user switches to another app, but Escape works only 'while the panel is the key window', and the panel has a close button and Retry. If clicking the panel activates VibeFlow, the frontmost app changes and that counts as switching apps, so the click ends the conversation. The design does not say the panel is a non-activating panel, or that VibeFlow's own panel is excluded from the switch rule.

**Remedy**

> Specify the panel as a non-activating NSPanel that can become key without activating VibeFlow. Define 'switching apps' as the frontmost app changing to something other than the conversation's source app, and exclude VibeFlow's own windows.

### R2-5 — completeness

**Problem**

> Barge-in covers playback and Claude generation, but not the gap after the answer text arrives while TTS synthesis is still in flight and nothing is playing yet. The design does not say whether that synthesis is cancelled, or whether the answer counts as interrupted (kept) or unanswered (dropped). Conversation-mode overlaps are also undefined: key down while a question is still transcribing, and Shift-forced dictation while an answer is speaking (does playback stop?).

**Remedy**

> Extend the conversation state rules: key down during TTS synthesis cancels it and keeps the answer text marked '(interrupted)' (or drops it, whichever is chosen); key down while a question is transcribing is ignored; and say whether forced dictation stops or keeps playback.

### R2-6 — clarity

**Problem**

> The 3 s 'key up to first answer audio' target depends on whether TTS is streamed. The design names the answer model and says it is non-streaming, but it does not say whether ElevenLabs or Apple TTS synthesis for answers is streamed or done in one piece before playback starts.

**Remedy**

> State whether answer TTS streams (playback starts on the first audio chunk) or is synthesized in one piece, and confirm the 3 s budget holds for that choice.

### R2-7 — completeness

**Problem**

> Retry 're-sends the last question', but when the failure is the question's transcription there is no question text to re-send. The design does not say whether the recorded audio is kept so it can be transcribed again.

**Remedy**

> Keep the last question's audio until its turn completes, and make Retry pick up at the step that failed (transcription, Claude or TTS).

### R2-8 — feasibility

**Problem**

> TextInserter pastes by pressing 'Edit > Paste' via Accessibility. Menu titles are localized: on a German system they read 'Bearbeiten > Einfügen', and some Electron apps and terminals have no standard Edit menu. Matching by title would fail for the primary user.

**Remedy**

> Find the paste menu item by its Cmd-V key equivalent or AX identifier rather than its title, with a synthesized Cmd+V fallback, and include a German-locale run in the paste reliability spike.

### R2-9 — clarity

**Problem**

> The inactivity timeout 'resets on any key press or panel interaction'. 'Any key press' could mean only the push-to-talk key, or any keystroke system-wide. The second would need a global keyDown monitor that the design does not otherwise have.

**Remedy**

> Say that only push-to-talk presses and panel interaction reset the timer, or else specify the global key monitoring it requires.

### R2-10 — clarity

**Problem**

> The empty-transcript rule refers to 'the Whisper no-speech marker', but the OpenAI-compatible transcription API returns no such marker. It offers no_speech_prob in verbose_json, and Whisper often hallucinates stock phrases such as 'Thank you.' on silence. The detection rule cannot be implemented as written.

**Remedy**

> Define detection concretely: request verbose_json and treat no_speech_prob above a threshold as no speech, and/or keep a small list of known silence hallucinations. Say what applies to the Apple transcriber.

### R2-11 — completeness

**Problem**

> The transcriber fallback table leaves some responses unclassified: 400 and 413 for both providers, 429 for a custom URL, and a custom endpoint with no key configured. Whether these fall back to Apple or surface as Last error is undefined.

**Remedy**

> Add a default row ('any other 4xx surfaces as Last error') and say whether a custom URL may be used without a key.

### Prior finding evidence

**R1-6 → R2-5 (persisting)**

> The dictation state machine and barge-in now cover dictation overlaps, Claude generation and playback, and Ending cancels everything in flight. Barge-in while answer TTS synthesis is still in flight, which the original finding named explicitly, is still undefined.

**R1-14 → R2-6 (persisting)**
