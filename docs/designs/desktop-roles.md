## Problem Statement

The user works in role-based macOS desktops (Spaces): Personal (personal Chrome profile, Spotify,
WhatsApp), Comms (WhatsApp Business, Mail, Slack), Build (Claude, ChatGPT, a browser, a text
editor). Each setup should stay the same every day, and each desktop should be recognisable at a
glance. Existing tools fall short on all four counts the user picked: the setup drifts and needs a
manual rebuild, Chrome profiles cannot be pinned to different desktops, desktops all look the same,
and tiling window managers (yabai, AeroSpace) are too heavy.

v1 scope, in the user's words: "morning and glance. fix drift later".

## What Makes This Cool

- **Roles, not desktops.** A desktop gets a name and a color. The menu bar shows the role name in
  its color, and a generated tint wallpaper makes the translucent menu bar (and the monitor)
  carry the same color. You know where you are without reading anything.
- **One key in the morning.** VibeFlow walks the desktops and opens only what is missing, each
  window on its own desktop, including the right Chrome profile with its tabs.
- **It sidesteps the wall every other tool hits.** Other tools try to *move* windows into Spaces,
  which macOS blocks with SIP on. VibeFlow *opens windows in place*: it makes the target desktop
  active first, then opens the window, so the window is born where it belongs. The same walk sets
  each desktop's wallpaper, because macOS stores the wallpaper per active Space.

## Constraints

- Lives inside VibeFlow (Swift 6 / SwiftUI, menu bar app, not sandboxed, already holds the
  Accessibility permission). No server, no database (global rule: simplest viable architecture).
- No SIP changes, no writes to private macOS state.
- Laptop plus an external monitor.
- Settings stay minimal (one new tab at most).

## Premises

1. A Role = a desktop number + name + color + a list of items to open (apps; Chrome profile +
   URLs). Roles bind to desktop numbers, not to macOS's internal Space IDs.
2. VibeFlow never moves existing windows. It opens missing windows while the right desktop is
   active. Single-window apps can additionally use the Dock's own "Assign to This Desktop", set by
   the user.
3. The tint is a generated solid or gradient wallpaper per desktop, applied to every connected
   display; the menu bar shows the role name in its color next to the existing clock label.
4. The current desktop is read with a read-only private call (as Spaceman does); switching
   simulates Control+1..9, which needs "Switch to Desktop N" enabled in Keyboard Shortcuts.
5. **Revised again 2026-11-03, after trying it:** "Displays have separate Spaces" stays **on**. In the
   user's words: "often im just switching 1 screen and get confused by both switch". Mission
   Control numbers desktops across screens (for example 1-3 on the laptop, 4-5 on the monitor) and
   Control+N switches only the screen that desktop lives on, so a role binds to one desktop number,
   which lives on one screen; its tint goes on that screen only, and the morning walk switches one
   screen at a time. The menu bar shows on every screen again. New risk for the spike: unplugging
   the monitor moves its desktops to the laptop and can renumber them.
   (Earlier revision, 2026-11-02, after the office-hours second opinion: separate Spaces off, both
   screens switch together. Dropped because linked switching confused the user.)
6. Drift fixing, Clock out (hide work apps + Focus on switching to Personal) and voice switching
   are out of v1.

## Approaches Considered

### Approach A: Glance + Launch list
Tint, role label and a key that opens every item on every desktop with no checks. Ruled out:
pressing the key twice opens duplicate windows, so the key is not safe to press.

### Approach B: Verified Roles (chosen)
See Recommended Approach.

### Approach C: Snapshot-first
Arrange a desktop by hand and "Remember as Comms"; the morning key replays it. Deferred: most
moving parts (Automation permission per browser for tab URLs). It can sit on B's engine later.

## Recommended Approach

**Approach B: Verified Roles.** The morning key only feels good if it is safe to press any time,
and B's planner is the base for drift fixing later.

**Core (VibeFlowCore, pure, Swift Testing):**
- `Role { id, name, colorHex, desktopNumber, items }` and
  `RoleItem = .app(bundleID) | .chrome(profileDirectory, urls)`; Codable, stored in UserDefaults
  like other settings.
- `LaunchPlanner.plan(role:, present:) -> [LaunchStep]`: given what is already on a desktop,
  returns only what to open. Tests cover empty desktop, everything present, partial, and
  unresolvable items.

**App side:**
- `SpacesProbe`: read-only private calls loaded with `dlsym` (Space list in order, active
  Space). Only regular desktops get numbers (1..9, counted the way Control+N counts them);
  full-screen app Spaces get no number and show no role label. Returns `.unknown` on any
  failure; nothing launches while unknown. Roles follow the number: if the user reorders desktops
  in Mission Control, label and tint move with the number, not with the windows (documented in
  the Desktops tab).
- `DesktopWalker`: at the start, compares the probe's desktop count with the highest role
  number; roles on missing desktops are skipped as unresolved ("Create desktop N in Mission
  Control"), never timed out. Then posts Control+N with `CGEvent`, waits for
  `NSWorkspace.activeSpaceDidChangeNotification` plus a probe that confirms the number, times out
  after 2 s and marks the role unresolved. After every launch it re-probes; if the active desktop
  changed unexpectedly, it switches back with Control+N and marks that item unresolved; if
  switching back fails, it stops the walk and reports. At the end it returns to the starting
  desktop; if the walk started on a full-screen Space, it ends on desktop 1 and the report says
  so. Pressing the key again cancels.
- `WindowInventory`: on the active desktop, lists windows through the Accessibility API
  (`AXWindows` per running app, assumed to report only the current Space's windows; spike
  question). Across all desktops, `CGWindowListCopyWindowInfo` (owner PID and layer only, no
  titles, so no Screen Recording permission) tells whether an app has windows anywhere.
- **Real window** (for the cross-desktop check): layer 0, bounds at least 100 x 100 pt,
  alpha > 0; phantom windows of Electron apps or apps launched hidden do not count.
- **Planner rules (never move, never duplicate), first match wins:**
  - App item, a window of that app is on this desktop (AX inventory): already there.
  - App item, app not running or with no real window anywhere: open it here.
  - App item, app has real windows only on other desktops: do not launch (activation would jump to that
    desktop, and single-window apps like Mail, Slack and WhatsApp cannot be on two desktops);
    report unresolved "open on another desktop". The Desktops tab suggests the Dock's
    "Assign to This Desktop" for such apps.
  - Chrome item, matching profile window identified on this desktop: already there.
  - Chrome item, profile cannot be identified (fallback in Open Question 1) and any Chrome window
    is on this desktop: never "already there", never launched again; reported unresolved
    "check profile". No Chrome window on this desktop: open it.
- Launching: apps through `NSWorkspace.openApplication`; Chrome through
  `open -na "Google Chrome" --args --profile-directory=<dir> --new-window <urls>`. Arrival
  check: poll every 200 ms for a window of that PID on the current desktop that was not in the
  pre-launch inventory; budget 8 s per item (15 s when the app was not running). Not seen in time:
  unresolved, never relaunched within the same walk.
- Chrome at login: if Chrome is not running, the walker launches it with the first Chrome item,
  then waits until its window count is stable for 2 s (max 15 s) before taking any inventory,
  so restored session windows are counted, not duplicated. The setup check warns when a role's
  Chrome profile restores the previous session on startup (Chrome's per-profile "On startup"
  setting) and recommends "Open the New Tab page".
- `RoleTint`: renders a solid or gradient PNG per role into Application Support and applies it
  with `NSWorkspace.setDesktopImageURL(_:for:options:)` for every screen while on that desktop;
  skips it when `desktopImageURL(for:)` already matches. Re-apply policy: never an unprompted walk.
  On `activeSpaceDidChangeNotification` and on screen-parameter changes (monitor attached, wake),
  VibeFlow checks and fixes only the current desktop's wallpaper; other desktops are fixed when
  you next visit them or press the morning key.
- Setup check: reads whether separate Spaces are off, auto-rearrange is off, "When switching to
  an application, switch to a Space with open windows" is off, Switch to Desktop 1..N shortcuts
  are on, and enough desktops exist (com.apple.spaces, com.apple.dock, com.apple.symbolichotkeys,
  `NSGlobalDomain AppleSpacesSwitchOnActivate`, read only), and shows each missing item with a
  button that opens the right System Settings pane.

**UI:**
- Menu bar: role name in its color next to the clock label. The clock label currently hides
  without configured world clocks (VibeFlowApp.swift); the role label must show either way.
  Outside any role: no label.
- Settings: one new "Desktops" tab (SettingsTab): setup check rows, then the role list (name,
  color, desktop number, items; app picker plus Chrome profile picker read from Chrome's
  Local State file).
- Morning key: a new `Shortcuts` entry, plus a "Set up desktops" menu item. Ends with a short
  report in the menu panel: opened N, already there N, unresolved N (with reason).

## Open Questions

1. **Chrome profile detection (spike).** Does the Accessibility title (or another AX attribute)
   of a Chrome window carry the profile name on macOS? If not, the fallback planner rule above
   applies: a Chrome window of unknown profile is reported "check profile", never counted as
   already there.
2. **Where does a new Chrome window land** when another Chrome window is open on a different
   desktop and Chrome is unassigned in the Dock? (Codex High finding; spike step 1.)
3. **Default key.** None proposed: voice keys own Option + `,` `.` `-`. Menu item only until the
   user picks one in Settings, or the user names a default.
4. **Wake and display changes.** How often does the per-desktop wallpaper get lost on sleep or
   monitor unplug/replug? The re-apply policy above handles it either way; the answer only
   decides whether the drift is visible often enough to matter.
5. **AXWindows per Space (spike).** Does `AXWindows` really list only the current Space's
   windows, and does it include minimized windows and windows of hidden apps? If it lists all
   Spaces, the inventory must intersect AX windows with `CGWindowList` on-screen windows instead.
6. **Chrome session restore (spike).** Where do restored windows land when Chrome starts during
   the walk, and does `open -na ... --new-window` trigger restore?
7. **Phantom windows (spike).** Does `CGWindowList` report windows for Slack, WhatsApp and Mail
   launched hidden at login, and does the real-window filter above exclude them?

## Success Criteria

- After login, one key leaves every role desktop with its items, correct Chrome profiles and tint,
  and returns to the starting desktop; anything it could not do is listed as unresolved with a
  reason.
- Pressing the key a second time never opens a duplicate: every item reports "already there" or,
  where VibeFlow cannot be sure (unknown Chrome profile, app open on another desktop),
  "unresolved".
- Works the same with the monitor attached and detached and after sleep: the current desktop's
  tint is fixed at once, every other desktop's on its next visit or morning key; VibeFlow never
  switches desktops without a key press.
- The menu bar label always matches the active desktop's role, or shows nothing / "Unknown
  desktop" when it cannot tell; it never shows a wrong role.
- No SIP changes, no private writes; Core planner covered by Swift Testing.
